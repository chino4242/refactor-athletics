**Date:** 2026-06-17

## Epic Summary

Full app rewrite from v1 monolith to 3-screen SNES-styled RPG fitness app.

- **Screens delivered:** Power Level, Arena, Train
- **Key systems:** Battle Mode engine, program resolver, 5-step onboarding, profile reskin
- **Files touched:** 100+ modifications
- **Tests:** 236 passing across 22 test files
- **Outcome:** App in daily active use during 75-day challenge with live tester

---

## What Went Well

- **Tight focus** — 3 screens done well beats 10 screens half-built. The decision to cut v1 features and focus on Power Level / Arena / Train was correct.
- **Battle Mode engine** — 1200+ line component handling lifting, duration, cardio, supersets, crits, combos, rest events. Complex but functional.
- **Shared program resolver** — Eliminated duplicate logic between schedule API and workout API. Single source of truth for "what exercises does this user do today?"
- **Daily active use** — The app is being used in a real 75-day challenge. Ultimate validation.
- **Pixel aesthetic** — SNES feel achieved without sacrificing readability of workout data.

---

## What Didn't Go Well

### Pattern 1: PostgREST Query Assumptions
- `.single()` on zero-row results caused 406 errors in 13 places
- Non-existent `reps` column in queries caused 400 errors
- Went undetected until real usage — no integration tests against actual Supabase behavior

### Pattern 2: Platform Divergence Discovered Late
- iOS HealthKit returns string types ("yoga"), Android returns numeric codes (83)
- The @capgo plugin and custom Kotlin plugin have different response shapes
- Never caught because testing happened on one platform at a time
- iOS provisioning profile was stale — feature worked in code, failed at deployment layer

### Pattern 3: Large Components Accumulating Complexity
- BattleView.tsx is 1200+ lines with 135 modifications across the project
- Every new feature gets added to the same file
- Blast radius of any change is high

### Root Cause (Systemic)
> We build forward fast but don't validate the connections between systems until a user hits them.

---

## Key Lessons

1. **Focus pays off** — 3 screens done well > 10 screens half-built
2. **Happy path isn't enough** — test the seams between systems
3. **Platform-specific behavior must be verified, not assumed**
4. **Free-text names in the DB shouldn't drive display labels** (Tuesday-on-Wednesday bug)
5. **Deployment pipeline is part of the feature** — code that can't reach the user isn't done
