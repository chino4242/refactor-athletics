# Decision Log — Push Notifications PRD

## Decisions

### D-1: Notification Categories (2026-07-08)
**Decision:** Include all categories from brainstorm — engagement/motivation, rank warnings, social/competitive, scheduled/contextual, and user preferences.
**Rationale:** User confirmed "this all looks great" for the full list. MVP scope trims to the highest-impact subset.

### D-2: Fast Path Selected (2026-07-08)
**Decision:** Draft full PRD without interactive coaching path.
**Rationale:** User has clear vision, confirmed notification types, and wants to move quickly to implementation.

### D-3: MVP Scope (2026-07-08)
**Decision:** MVP includes streak warnings, quest incomplete, rank-up proximity, duel received, workout day reminder, category toggles, quiet hours, and basic logging. Phase 2 adds hydration, party milestones, group challenges, smart timing, rank decay warnings, re-engagement, weekly summary.
**Rationale:** Ship the highest-retention notifications first (streak + social), layer in contextual ones after measuring effectiveness.

### D-4: Notifications Ship Before Rank Decay (2026-07-08)
**Decision:** Build push notifications as a standalone feature. Rank decay warnings will be added later when rank decay is implemented.
**Rationale:** Notifications provide immediate retention value without the rank decay dependency. Decoupling avoids blocking on a larger feature.

### D-5: Permission Prompt During Onboarding (2026-07-08)
**Decision:** Request notification permission as a dedicated step in the onboarding wizard, after health sync.
**Rationale:** Captures users at peak engagement (initial setup excitement). Avoids interrupting their first training session. Aligns with the existing onboarding pattern of asking for permissions (health sync is already there).

### D-6: Themed RPG Notification Copy (2026-07-08)
**Decision:** RPG mode users receive themed notification copy using rank names and RPG language. Classic mode users receive themed notification copy. Templates have both variants.
**Rationale:** Consistent with the experience mode system throughout the app. Reinforces immersion for RPG users without confusing Classic users.

### D-7: FCM Unified Delivery (2026-07-08)
**Decision:** Use Firebase Cloud Messaging as the unified push delivery layer for both iOS and Android.
**Rationale:** Single API reduces backend complexity. Capacitor plugin designed for FCM. APNs key uploaded to Firebase project lets FCM proxy iOS delivery. Latency difference (18ms) is imperceptible. Avoids maintaining two separate send paths.

### D-8: Daily Cap of 1-2 Notifications (2026-07-08)
**Decision:** Maximum 2 notifications per day per user. Priority queue selects the most relevant when multiple would fire.
**Rationale:** Matches Duolingo's conservative approach. Prevents notification fatigue. Each notification must earn its slot. Can always increase later if engagement data supports it.
